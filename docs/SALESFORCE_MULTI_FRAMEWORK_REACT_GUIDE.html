Executive Overview & Capabilities

Native Open-Source Frontend on Salesforce Platform

Historically, Salesforce forced developers building SPAs into the proprietary Lightning Web Component (LWC) framework, or into complex workarounds such as packaging React inside Static Resource .zip files with lwc:dom="manual", or embedding external web apps within restrictive iframe / Visualforce tags.

Salesforce Multi-Framework Development bridges this gap. It introduces native platform support for modern open-source web frameworks—specifically React with Vite and TypeScript—treating React apps as first-class deployable metadata under the UIBundle architecture.

⚡

UIBundle Metadata

Treats compiled Vite/React bundles as first-class Salesforce metadata alongside Apex and LWC.

🔐

Zero OAuth Dance

Inherits authenticated user sessions, cookies, and CSRF tokens automatically without Connected Apps.

📊

Direct UI API GraphQL

Query and mutate Salesforce records directly in TypeScript via @salesforce/platform-sdk without custom Apex.

🚀

Local Proxy HMR

Run sf ui-bundle dev with 50ms Hot Module Replacement connected live to your cloud org.

Org Prerequisites & Setup Steps

1. Enable Digital Experiences in Salesforce Setup

Navigate to Setup > Quick Find: Digital Experiences > Settings. Check Enable Digital Experiences, choose your domain, and save. This provisions the core Network and CustomSite metadata engines.

2. Enable Multi-Framework Support

In Setup, search for React Development with Agentforce Vibes or Multi-Framework and toggle to Enabled. This registers the UIBundle handler and GraphQL UI API non-LWC endpoints.

3. Verify Salesforce CLI Capabilities

Confirm that your CLI includes the UI Bundle toolchain:

PowerShell 
sf help ui-bundle
sf template generate ui-bundle --help
4. Run Local Dev with Reverse Proxy Authentication

Start local development without deploying code. CLI proxy attaches your active session tokens to GraphQL requests:

PowerShell 
sf ui-bundle dev --name ReactExperiencePoc --target-org learn_dc --open
A

Pathway A: Internal Application Deployment (App Launcher)

🎯 Internal Employee Experience

This pathway hosts a full-width React 19 SPA inside Salesforce Lightning Experience. Internal authenticated users discover and launch it directly from the 9-dot App Launcher, inheriting all platform permissions and user sessions.

1. How Internal Deployment Works

When deploying for internal employees, the React SPA is compiled into static production assets in uiBundles/ReactExperiencePoc/dist. A Salesforce CustomApplication metadata definition points directly to the bundle using <uiBundle>c__ReactExperiencePoc</uiBundle>. A PermissionSet assigns application visibility so authorized profiles see the app in the App Launcher.

2. Files Created & Modified for Internal Deployment

File 1: ReactExperiencePoc.uibundle-meta.xml

Path: force-app/main/default/uiBundles/ReactExperiencePoc/ReactExperiencePoc.uibundle-meta.xml

File 5: Home.tsx & graphqlClient.ts (Interactive POC Screen)

Path: force-app/main/default/uiBundles/ReactExperiencePoc/src/pages/Home.tsx

Demonstrates local React reactive state management and native UI API GraphQL queries via @salesforce/platform-sdk:

Home.tsx (GraphQL + React State) 
import { useState } from 'react';
import { Card, CardHeader, CardTitle, CardDescription, CardContent } from '../components/ui/card';
import { Button } from '../components/ui/button';
import { executeGraphQL } from '../api/graphqlClient';

export default function Home() {
  const [count, setCount] = useState(0);
  const [accounts, setAccounts] = useState([]);
  const [loading, setLoading] = useState(false);

  const fetchAccounts = async () => {
    setLoading(true);
    const query = `
      query getAccounts {
        uiapi {
          query {
            Account(first: 5) {
              edges { node { Id Name { value } } }
            }
          }
        }
      }
    `;
    const response = await executeGraphQL(query);
    setAccounts(response?.uiapi?.query?.Account?.edges?.map(e => e.node) || []);
    setLoading(false);
  };

  return (
    <div className="max-w-5xl mx-auto p-8 space-y-6">
      <h1 className="text-3xl font-bold text-gray-900">React inside Salesforce (Internal App)</h1>
      <div className="grid grid-cols-2 gap-6">
        <Card>
          <CardHeader><CardTitle>Reactive State: {count}</CardTitle></CardHeader>
          <CardContent>
            <Button onClick={() => setCount(c => c + 1)}>Increment (+1)</Button>
          </CardContent>
        </Card>
        <Card>
          <CardHeader><CardTitle>Salesforce GraphQL UI API</CardTitle></CardHeader>
          <CardContent>
            <Button onClick={fetchAccounts} disabled={loading}>Query Accounts</Button>
          </CardContent>
        </Card>
      </div>
    </div>
  );
}

Pathway B: External Experience Cloud Site Deployment (LWR)

🌐 External & Public Guest Experience

This pathway hosts the application on a public Experience Cloud site (Build Your Own LWR template). External visitors and unauthenticated guests can access the site freely without a login wall.

1. Key Challenges We Encountered & How We Solved Them

🔓

Challenge 1: Login Prompt Wall

Fix: Set Network status to Live, site authentication to AUTHENTICATED_WITH_PUBLIC_ACCESS_ENABLED, and route to Public.

🏜️

Challenge 2: "Start Building" Desert

Fix: Replaced the default community_builder:htmlEditor desert placeholder in sfdc_cms__view/home/content.json with c:reactExperienceViewer.

🛡️

Challenge 3: Guest Permset Limits

Fix: Created ReactExperienceGuestAccess with only <classAccesses> to prevent the TABSET_LIMIT_EXCEEDED error on guest profiles.

🚀

Challenge 4: Draft vs Published CDN

Fix: Deployed CMS metadata updates the Draft builder state; clicked Publish in Experience Builder to push to live CDN.

File 6 & 7: reactExperienceViewer (LWC Component)

Path: force-app/main/default/lwc/reactExperienceViewer/

Renders the interactive UI on the Experience page with reactive state and backend Apex queries:

reactExperienceViewer.js 
import { LightningElement, track } from 'lwc';
import getSampleAccounts from '@salesforce/apex/ReactExperienceController.getSampleAccounts';

export default class ReactExperienceViewer extends LightningElement {
    @track count = 0;
    @track accounts = [];
    @track isLoading = false;
    @track errorMessage = null;

    get hasAccounts() { return this.accounts && this.accounts.length > 0; }
    handleIncrement() { this.count += 1; }
    handleReset() { this.count = 0; }

    async handleFetchAccounts() {
        this.isLoading = true;
        this.errorMessage = null;
        try {
            const data = await getSampleAccounts();
            this.accounts = data || [];
        } catch (error) {
            this.errorMessage = error?.body?.message || 'Unable to fetch accounts in guest context.';
        } finally {
            this.isLoading = false;
        }
    }
}

File 8: ReactExperienceController.cls (Apex Backend)

Path: force-app/main/default/classes/ReactExperienceController.cls

Provides guest-compatible data queries running in WITH USER_MODE:

ReactExperienceController.cls 
public with sharing class ReactExperienceController {
    @AuraEnabled(cacheable=true)
    public static List<Account> getSampleAccounts() {
        try {
            return [SELECT Id, Name FROM Account WITH USER_MODE LIMIT 5];
        } catch (Exception e) {
            return new List<Account>();
        }
    }
}

Troubleshooting, Gotchas & Best Practices

⚠️ Always Remember Experience Builder "Publish"

Deploying metadata under digitalExperiences/ updates only the Draft builder workspace. The public CDN serving guests will not reflect your changes until you click Publish in Experience Builder!

⚠️ Never Assign Standard Apps to Guest Users

Guest users cannot have application visibilities. Adding <applicationVisibilities> to guest permission sets triggers TABSET_LIMIT_EXCEEDED (limit of 0 standard apps).

ℹ️ Guest User Sharing Rules for Live Records

When executing SOQL under guest context with WITH USER_MODE, create a Guest User Sharing Rule in Setup > Sharing Settings so the guest profile can read records.

ℹ️ Always Dev via Proxy Port (4546)

When running sf ui-bundle dev, access the app at http://localhost:4546 rather than the direct Vite port (5173). The proxy injects the authenticated session tokens required for GraphQL calls.
